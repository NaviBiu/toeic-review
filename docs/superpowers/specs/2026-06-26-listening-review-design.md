# TOEIC 听力错题知识点 + 间隔复盘系统 设计文档

- 日期:2026-06-26
- 所属计划:[[project_3month_toeic_portfolio_plan]] 的 Case B(用户 3 个月 TOEIC + 作品集计划)
- 状态:设计已与用户逐项确认(含基于外部审查反馈的修订)

## 1. 背景与目标

用户在准备 TOEIC 听力时,会把每天练习中遇到的生词/短语知识点(不是原题)整理成 Word/PDF 笔记,按 Part(1-4)和日期分块记录。目前这些笔记只是静态文档,没有复盘机制,也没有按场景分类,记完就很少再回顾。

目标:做一个独立的网络应用,把这些笔记变成一个"持续更新的错题库",具备:

1. 把手写笔记自动导入并结构化(借助 AI 解析 + 场景分类)
2. 基于艾宾浩斯记忆曲线的间隔复盘机制,自动安排"今天该复盘什么"
3. 独立的模考成绩记录,用于发现 Part/场景层面的薄弱环节
4. 全平台(电脑/iPad/iPhone)可访问,数据统一

本工具是用户 3 个月作品集计划中 Case B(TOEIC 学习工具)的第一阶段实现,聚焦**听力**;阅读出题模块明确推迟到后续阶段,但数据结构预留了扩展空间。

## 2. 范围

**本次做的:**
- 听力错题知识点的导入、复盘、间隔调度
- 模考成绩记录(Part 正确率必填、场景正确率选填)
- 场景分类采用"大类+细类"两级(见第 12 节附录)
- 简单统计页面(错题库聚合统计 + 模考历史)
- 密码门访问控制(含会话有效期)
- 一键导出全部数据为 JSON,作为简单的手动备份手段
- 独立的"手动添加一条知识点"入口,不依赖文档导入

**明确不做 / 推迟到以后:**
- 阅读(Reading)题目生成模块——数据表预留 `skill` 字段占位,不在本次实现任何相关功能
- "完整测试/抽样测试"两种模式——用队列按优先级排序 + 按场景筛选替代,效果已足够
- 复盘事件级别的历史日志/趋势图表——统计页面用知识点表上的聚合字段(`correct_count`/`wrong_count`)计算,不记录每次复盘的独立事件
- 确认列表的批量编辑(批量改 Part/场景)——每日小份导入下单次新增条目不多,逐条改成本不高
- 操作审计日志系统——个人单用户工具,真出问题可直接查数据库排查
- AI API 调用频率限制/预算上限机制——当前用量级的 token 成本可忽略,无失控风险
- 自动定时备份/多版本云端备份——用一键导出 JSON 作为足够的手动保险,不做更复杂的机制
- 离线模式(无网络时复盘)
- 多用户/多账号体系
- "忘记密码"自助找回流程
- Case A(AI 新闻 agent)和个人网站的任何改动——按用户要求本次完全不碰

## 3. 整体架构

- 新建独立项目仓库(本设计文档所在的 `toeic-review/`),与现有 `personal-website`(纯静态站点)完全分离,互不影响。未来个人网站展示 Case B 案例时,只需添加文字介绍/截图/链接,不需要合并代码。
- 技术栈:Next.js(前端页面与后端 API Route 在同一项目内)。
- 代码托管:GitHub(用户已有账号)。
- 部署:Vercel(用 GitHub 账号登录,push 后自动部署,获得永久访问网址)。
- 数据库:Vercel Postgres(随 Vercel 项目一起创建,免费额度)。
- AI 调用:Anthropic Claude API,用于①导入文档解析为结构化记录、②缺失释义/例句补全、③场景大类+细类自动分类。需要用户注册 Anthropic API Key,存为 Vercel 环境变量,不出现在代码或前端。
- 访问控制:简单密码门——所有页面与 API 请求都需要先验证一个共享密码(存为环境变量,纯文本比较;该密码不进入应用自己的数据库,不存在"数据库被脱库导致密码批量泄露"的场景,哈希在此处不会带来实际安全收益,故不做哈希存储)。验证后用 cookie 维持登录状态,cookie 设 30 天有效期,过期需重新输入密码。
- 设备访问:电脑/iPad/iPhone 浏览器直接打开同一个网址,iPad/iPhone 可"添加到主屏幕"获得类 App 体验。需要联网使用,不支持离线。

## 4. 数据模型

### 4.1 `knowledge_points`(错题知识点表)

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 主键 | |
| term | text | 单词/短语原文 |
| meaning | text | 释义(笔记缺失时由 AI 补全) |
| example | text | 例句(笔记缺失时由 AI 补全) |
| notes | text, 可空 | 用法提示/高频备注。仅当原始笔记里本身就有这类说明时才存;AI 不会主动编造这部分内容 |
| part | enum(1\|2\|3\|4) | 对应 TOEIC 听力 Part1-4 |
| scenario_major | enum,14 选 1 | ETS 官方 13 类测验情境 + "未分类" 兜底项,完整列表见第 12 节附录。AI 导入时自动判断,用户可在导入确认步骤或之后任何时候手动修改 |
| scenario_minor | text(受限于所选大类) | 该大类下的细分场景。每个大类的可选细类 = 附录中该大类列出的细类列表 + 通用兜底选项"未分类"(无论选了哪个大类,下拉菜单里永远都能选到"未分类"这一项);大类判断有信心但细类拿不准时就选这个通用兜底项;若大类本身判断为"未分类",细类直接固定为"未分类"。界面上以下拉菜单呈现,选项随所选大类动态变化,不支持自由输入新细类 |
| skill | enum,目前固定 'listening' | 占位字段,为未来接入 Reading 模块预留,本次不启用相关逻辑 |
| date_added | date | 笔记中记录的学习日期(不是导入操作的日期)。若笔记中没有明确日期,默认取本次导入操作当天;AI 解析时负责把笔记里出现的各种日期写法统一转换成标准格式;不允许晚于今天的日期,解析出未来日期会在确认列表中标红,要求用户手动修正 |
| status | enum('active'\|'mastered') | mastered = 已永久退役,不再出现在每日复盘队列;用户可在"已掌握"列表中手动改回 active(重新从连续答对 0 次开始计时) |
| correct_streak | int,默认 0 | 当前连续答对次数,任意一次答错清零;达到 3 即转为 mastered。同时直接决定下次复盘间隔,见第 7 节 |
| correct_count | int,默认 0 | 终身累计答对次数,仅用于统计,不参与调度逻辑 |
| wrong_count | int,默认 0 | 终身累计答错次数(含"重复导入触发"的情形,见 5.3) |
| next_review_date | date,可空 | 下次该复盘的日期;`status = mastered` 时为 NULL,表示当前没有排定的复盘日期 |
| last_reviewed_date | date,可空 | 上次复盘日期 |
| created_at / updated_at | timestamp | 常规记录时间戳 |

唯一性约束:`(term, part, scenario_major, scenario_minor, skill)` 组合用于导入查重判断(比较时忽略大小写、首尾空格与常见标点差异)。同一个词/短语在不同场景下可能是完全不同的含义(例如 "check" 在金融场景是支票、在办公室场景是核对),所以查重必须把场景也纳入判断,否则会把两个不同含义的知识点错误合并成一条。约束里包含 `skill` 是为未来 Reading 模块预留:`skill` 当前固定为 'listening',现在加不加这个字段效果上没区别,但等以后 Reading 模块真接入、出现 `skill = 'reading'` 的记录时,能避免和听力的同名知识点被误判成同一条。

手动编辑已有记录的 `part`、`scenario_major` 或 `scenario_minor` 时,同样要按这个唯一性组合校验:若改动后会跟另一条已存在的记录(自身除外)完全重复,阻止保存并提示"这个组合已经存在,请检查是否要合并",不允许出现两条完全相同组合的记录。

## 5. 导入流程

1. 用户每天在电脑上把当天新增的错题笔记(PDF/Word,只含当天新内容,不是累计文档)上传。
2. 后端将文档转为文字,调用 Claude API 解析为结构化记录:term、meaning、example、notes(如有)、part 与 date_added(从文档中的"Part几"标题和"时间:"行继承)。
3. 若某条记录缺 meaning 或 example,由 AI 生成合理的简洁内容补全;notes 字段不做这种补全,留空即可。
4. Claude 同时依据第 12 节附录的场景分类表,给每条记录判断 scenario_major 和 scenario_minor 两级标签;任何一级拿不准就标"未分类"。
5. 解析结果先展示为可编辑确认列表(每个字段,包括 part、scenario_major、scenario_minor,用户都可直接修改/删除),用户确认无误后才正式写入数据库。
6. 写入时按 `(term, part, scenario_major, scenario_minor, skill)` 查重,分三种情况处理(细节见 5.3):全新记录、已存在且为 active、已存在且为 mastered。若某一条写入失败(例如查重冲突需要人工决定),只影响这一条,其它正常的记录照常写入,不做整批回滚。

### 5.1 为什么改成"每日小份导入"而不是"累计大文档重复导入"

用户原本习惯把笔记写在同一份持续累加的文档里,每隔几天整份重新导入。这样每次导入都要重新处理全部历史内容,AI 解析的 token 消耗会随文档增长线性上升。改为"每天只导出/导入当天新增内容"后,每次导入的处理量只跟当天新增内容成正比,不会随历史积累变慢变贵,且不需要额外的"按内容指纹跳过已处理区块"机制,简化了实现。

### 5.2 确认列表中的冲突处理

若解析出的某条记录在数据库中已存在但字段内容不同,在确认列表中明确标出新旧差异,由用户选择保留哪个版本,不做静默覆盖。这里"内容不同"只可能出现在 `meaning`、`example`、`notes` 这三个描述性字段上——因为 `term`、`part`、`scenario_major`、`scenario_minor`、`skill` 本身就是判断"是否已存在"的查重键,两条记录能匹配上,这几个字段必然完全一致,不存在冲突,也不会被覆盖。`date_added` 同样不受这次导入影响,始终保留第一次记录该知识点时的日期,不会被新的导入日期覆盖。

### 5.3 重复 term+part+场景 的语义:不是误传,而是"又错了一次"

由于现在改为每日只导入新内容,同一个 `(term, part, scenario_major, scenario_minor, skill)` 组合在不同日期的导入中再次出现,代表用户在真实听力练习中又把这个知识点搞错了一次,是有意义的信号,不应被当作无意义的重复而直接忽略:

- 若该记录当前是 **active**:按一次"复盘答错"处理——`correct_streak` 清零、`wrong_count + 1`、`next_review_date` 设为明天。
- 若该记录当前是 **mastered**:自动复活——`status` 改回 active、`correct_streak` 清零、`wrong_count + 1`、`next_review_date` 设为明天。
- 若不存在:作为全新记录插入,`status = active`、`correct_streak = 0`、`next_review_date = 今天`(当天即可被抽到复盘,满足"当天抽查刚学内容"的需求)。

### 5.4 文档格式与解析失败处理

- 支持范围:文字版 PDF/Word(可直接提取文字的格式);不支持扫描图片版 PDF/OCR 识别——这次不做,以后如果笔记习惯变成手写扫描件再考虑加。
- 单次上传文件大小设一个合理上限(例如 5MB),日常单日新增笔记的体量远小于这个量级,正常使用不会触发。
- 上传格式不支持时,前端明确提示"不支持此文件格式,请上传文字版 PDF 或 Word"。
- AI 解析调用失败(超时/接口报错)或返回内容无法识别成结构化数据时,前端提示"解析失败,请重试";不会无声失败,也不会保存任何半成品数据。
- 提供独立的"手动添加一条知识点"入口(不依赖文档导入),可随时单独补一条记录,也作为解析持续失败时的退路。这个入口里 `term`、`part` 需要用户手动填;`meaning`/`example`/`scenario_major`/`scenario_minor` 默认留空,旁边提供一个"AI 自动补全"按钮——用户点了才调用 Claude 根据 term(和已填的 part)生成释义/例句并判断场景,不点就完全手动填,不强制依赖 AI。

## 6. 复盘流程与交互

1. "今日复盘"页面拉取所有 `next_review_date ≤ 今天` 且 `status = active` 的记录,按优先级排序(`wrong_count` 高、拖欠天数久的排前面),支持按场景(大类/细类)筛选,只复盘某个场景的到期内容,方便针对薄弱场景集中练习。
2. 逐条展示:先只显示 `term` → 用户点击"记得"或"不记得"(揭示答案前的主动回忆判断)→ 系统揭示 `meaning` + `example` + `notes`(如有)→ 用户自行核对,若发现刚才判断错了可以点"撤回"改选另一项 → 确认无误后点击"下一个"。
3. **撤回的边界**:撤回只在点击"下一个"之前有效;一旦进入下一条,上一条的结果即为最终结果,不可逆。因为在点击"下一个"之前什么都还没有写入数据库,撤回只是改变前端尚未提交的选择,不涉及任何数据库回滚。
4. 点击"下一个"时才正式落库这次结果(规则见第 7 节)。当前会话内用户可以随时关闭页面,未复盘的到期记录不会丢失,下次打开依然在队列里(只是会因为拖欠更久而排得更靠前)。
5. 队列为空时显示"今天没有需要复盘的内容"。
6. 错题库列表(非复盘模式,纯浏览)支持按 Part、按场景(大类/细类)筛选。
7. "已掌握"列表可单独查看所有 mastered 记录,并提供手动"移回错题库"操作(重置为 `status = active`、`correct_streak = 0`、`next_review_date = 今天`,立刻进入当天的复盘队列)。

## 7. 间隔复盘算法

间隔完全由 `correct_streak`(当前连续答对次数)直接驱动,不再单独存一个"曲线档位"字段。本质上是经典艾宾浩斯曲线最前两级(1天、2天)的简化版:"连续答对3次即移出复盘"这条规则决定了任何一条记录最多只会真正经历这两级间隔,更长的间隔(4/7/15/30天等)在这条规则下永远不会被触发,写入也用不到,故不保留。

- **答对(最终判定)**:`correct_count += 1`、`correct_streak += 1`。
  - 若此时 `correct_streak == 1`:`next_review_date = 今天 + 1 天`。
  - 若此时 `correct_streak == 2`:`next_review_date = 今天 + 2 天`。
  - 若此时 `correct_streak >= 3`:`status = mastered`,移出每日复盘队列,不再设置 next_review_date。
- **答错(最终判定)**:`wrong_count += 1`、`correct_streak = 0`,`next_review_date = 明天`(下次答对会重新从"1天后"开始算)。

由于答错会清零连续答对数,"常错的知识点"天然会一直停留在"1天后再考"这个最高频率上,无需额外设计加频规则。另外,由于"今日复盘"只拉取 `next_review_date ≤ 今天` 的记录,而任何一次复盘结果落库后新的 next_review_date 必然在明天或更后,所以同一条记录不会在同一天内被重复抽到复盘,不需要额外的"每日复盘次数上限"机制。

## 8. 模考成绩记录

独立入口"记录一次模考":用户输入模考日期,必须填写 Part1-4 各自的对题数/总题数,可选填任意数量的"场景(大类+细类):对题数/总题数"。保存后出现在统计页面的"模考历史"列表中,按日期排列,用于发现长期偏弱的 Part 或场景。这套数据与错题库的复盘记录完全独立,互不影响对方的计算逻辑。

## 9. 统计页面

两个独立区块:

1. **错题库统计**:当前 active 记录数、mastered 记录数、按 Part 汇总的历史正确率、按场景大类汇总的历史正确率(`correct_count / (correct_count + wrong_count)`)。数据来源是 `knowledge_points` 表上的聚合字段,不依赖单独的事件日志表。细类层级的数据仍然存在,但本次统计页面只展示大类层级的汇总图表;需要细类明细时可在错题库列表里按细类筛选查看,不在统计页面单独再做一层图表,避免本次范围过度扩大。
2. **模考历史**:按时间列出每次模考记录的 Part/场景正确率,表格形式,本次不做趋势图表。

## 10. 数据导出与备份

在统计页面提供一个"导出全部数据"按钮,点击后把 `knowledge_points`、`mock_exam_results`、`mock_exam_scenario_scores` 三张表的全部数据打包成一个 JSON 文件,由浏览器直接下载到本机,作为额外的手动备份手段。

不做自动定时备份、不做云端多版本备份机制——Vercel Postgres(底层是 Neon)本身通常自带一定程度的平台级时间点恢复能力,具体保留时长以实际开通时的版本为准;这个导出按钮只是想要更安心时随手点一下的额外保险,不是依赖它做灾难恢复的主要手段。

## 11. 安全与运行默认值

- 密码门:单一共享密码,存为 Vercel 环境变量,纯文本比较;验证后用 cookie 维持会话,cookie 设 30 天有效期,过期需重新输入密码。
- API Key(Anthropic):存为 Vercel 环境变量,不进入代码仓库或前端。
- 时区:统一按中国时间(UTC+8)计算"今天"以及到期日判断。
- 查重比较时忽略大小写、首尾空格与常见标点差异。
- 忘记密码:无自助找回流程,需要请求修改 Vercel 环境变量并重新部署。

## 12. 附录:场景分类表(大类 + 细类)

来源:ETS 官方 TOEIC 测验情境分类。AI 导入解析与手动编辑时,scenario_minor 的可选项严格限定为对应 scenario_major 下列出的细类,外加统一兜底项"未分类"。

1. **企业发展**:研究、产品研发
2. **外食**:商务/非正式午餐、宴会、招待会、餐厅订位
3. **娱乐**:电影、剧场、音乐、艺术、展览、博物馆、媒体
4. **金融/预算**:银行业务、投资、税务、会计、账单
5. **一般商务**:契约、谈判、并购、行销、销售、保证、商业企划、会议、劳动关系
6. **保健**:医疗保险、看医生、牙医、诊所、医院
7. **房屋/公司地产**:建筑、规格、购买租赁、电力瓦斯服务
8. **制造业**:工厂管理、生产线、品管
9. **办公室**:董事会、委员会、信件、备忘录、电话、传真、电子邮件、办公室器材与家具、办公室流程
10. **人事**:招考、雇用、退休、薪资、升迁、应征与广告、津贴、奖励
11. **采购**:购物、订购物资、送货、发票
12. **技术层面**:电子、科技、电脑、实验室与相关器材、技术规格
13. **旅游**:火车、飞机、计程车、巴士、船只、渡轮、票务、时刻表、车站、机场广播、租车、饭店、预订、脱班与取消
14. **未分类**:兜底项,无细类(scenario_minor 固定为"未分类")

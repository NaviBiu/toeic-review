# TOEIC 听力错题知识点 + 间隔复盘系统 设计文档

- 日期:2026-06-26
- 所属计划:[[project_3month_toeic_portfolio_plan]] 的 Case B(用户 3 个月 TOEIC + 作品集计划)
- 状态:设计已与用户逐项确认(含基于外部审查反馈的修订)

## 1. 背景与目标

用户在准备 TOEIC 听力时,会把每天练习中遇到的生词/短语知识点(不是原题)整理成 Word/PDF 笔记,按 Part(1-4)和日期分块记录。目前这些笔记只是静态文档,没有复盘机制,也没有按场景分类,记完就很少再回顾。

目标:做一个独立的网络应用,把这些笔记变成一个"持续更新的错题库",具备:

1. 把手写笔记自动导入并结构化(借助 AI 解析 + 场景分类)
2. 基于艾宾浩斯记忆曲线的间隔复盘机制,自动安排"今天该复盘什么"
3. 独立的模考成绩记录,用于发现 Part/场景层面的薄弱环节
4. 全平台(电脑/iPad/iPhone)可访问,数据统一

本工具是用户 3 个月作品集计划中 Case B(TOEIC 学习工具)的第一阶段实现,聚焦**听力**;阅读出题模块明确推迟到后续阶段,但数据结构预留了扩展空间。

## 2. 范围

**本次做的:**
- 听力错题知识点的导入、复盘、间隔调度
- 模考成绩记录(Part 正确率必填、场景正确率选填)
- 场景分类采用"大类+细类"两级(见第 12 节附录)
- 简单统计页面(错题库聚合统计 + 模考历史)
- 密码门访问控制(含会话有效期)
- 一键导出全部数据为 JSON,作为简单的手动备份手段
- 独立的"手动添加一条知识点"入口,不依赖文档导入
- 复盘和浏览时都可以直接删除"不需要再复习"的知识点(软删除,带撤销窗口)

**明确不做 / 推迟到以后:**
- 阅读(Reading)题目生成模块——数据表预留 `skill` 字段占位,不在本次实现任何相关功能
- "完整测试/抽样测试"两种模式——用队列按优先级排序 + 按场景筛选替代,效果已足够
- 复盘事件级别的历史日志/趋势图表——统计页面用知识点表上的聚合字段(`correct_count`/`wrong_count`)计算,不记录每次复盘的独立事件
- 确认列表的批量编辑(批量改 Part/场景)——每日小份导入下单次新增条目不多,逐条改成本不高
- 操作审计日志系统——个人单用户工具,真出问题可直接查数据库排查
- AI API 调用频率限制/预算上限机制——当前用量级的 token 成本可忽略,无失控风险
- 自动定时备份/多版本云端备份——用一键导出 JSON 作为足够的手动保险,不做更复杂的机制
- 离线模式(无网络时复盘)
- 多用户/多账号体系
- "忘记密码"自助找回流程
- Case A(AI 新闻 agent)和个人网站的任何改动——按用户要求本次完全不碰

## 3. 整体架构

- 新建独立项目仓库(本设计文档所在的 `toeic-review/`),与现有 `personal-website`(纯静态站点)完全分离,互不影响。未来个人网站展示 Case B 案例时,只需添加文字介绍/截图/链接,不需要合并代码。
- 技术栈:Next.js(前端页面与后端 API Route 在同一项目内)。
- 代码托管:GitHub(用户已有账号)。
- 部署:Vercel(用 GitHub 账号登录,push 后自动部署,获得永久访问网址)。
- 数据库:Vercel Postgres(随 Vercel 项目一起创建,免费额度)。
- AI 调用:Anthropic Claude API,用于①导入文档解析为结构化记录、②缺失释义/例句补全、③场景大类+细类自动分类。需要用户注册 Anthropic API Key,存为 Vercel 环境变量,不出现在代码或前端。
- 访问控制:简单密码门——所有页面与 API 请求都需要先验证一个共享密码(存为环境变量,纯文本比较;该密码不进入应用自己的数据库,不存在"数据库被脱库导致密码批量泄露"的场景,哈希在此处不会带来实际安全收益,故不做哈希存储)。验证后用 cookie 维持登录状态,cookie 设 30 天有效期,过期需重新输入密码。
- 设备访问:电脑/iPad/iPhone 浏览器直接打开同一个网址,iPad/iPhone 可"添加到主屏幕"获得类 App 体验。需要联网使用,不支持离线。

## 4. 数据模型

### 4.1 `knowledge_points`(错题知识点表)

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 主键 | |
| term | text | 单词/短语原文 |
| meaning | text | 释义(笔记缺失时由 AI 补全) |
| example | text | 例句(笔记缺失时由 AI 补全) |
| notes | text, 可空 | 用法提示/高频备注。仅当原始笔记里本身就有这类说明时才存;AI 不会主动编造这部分内容 |
| part | enum(1\|2\|3\|4) | 对应 TOEIC 听力 Part1-4 |
| scenario_major | enum,14 选 1 | ETS 官方 13 类测验情境 + "未分类" 兜底项,完整列表见第 12 节附录。AI 导入时自动判断,用户可在导入确认步骤或之后任何时候手动修改 |
| scenario_minor | text(受限于所选大类) | 该大类下的细分场景。每个大类的可选细类 = 附录中该大类列出的细类列表 + 通用兜底选项"未分类"(无论选了哪个大类,下拉菜单里永远都能选到"未分类"这一项);大类判断有信心但细类拿不准时就选这个通用兜底项;若大类本身判断为"未分类",细类直接固定为"未分类"。界面上以下拉菜单呈现,选项随所选大类动态变化,不支持自由输入新细类 |
| skill | enum,目前固定 'listening' | 占位字段,为未来接入 Reading 模块预留,本次不启用相关逻辑 |
| date_added | date | 笔记中记录的学习日期(不是导入操作的日期)。若笔记中没有明确日期,默认取本次导入操作当天;AI 解析时负责把笔记里出现的各种日期写法统一转换成标准格式;不允许晚于今天的日期,解析出未来日期会在确认列表中标红,要求用户手动修正 |
| status | enum('active'\|'mastered'\|'deleted') | mastered = 算法判定真正长期记住、自动退役;deleted = 用户在复盘或浏览时手动判定"不需要再复习",彻底退出复盘队列和错题库列表。两者都是软删除性质,记录本身不会被物理删除。用户可在"已掌握"列表中手动把 mastered 改回 active(重新从连续答对 0 次开始计时);`deleted` 只能在删除后的撤销窗口内变回 active,过期后没有自助恢复入口 |
| correct_streak | int,默认 0 | 当前连续答对次数,任意一次答错清零;达到 7(即完整走完一遍艾宾浩斯曲线的 6 个间隔后再答对一次)才转为 mastered。同时直接决定下次复盘间隔,见第 7 节 |
| correct_count | int,默认 0 | 终身累计答对次数,仅用于统计,不参与调度逻辑 |
| wrong_count | int,默认 0 | 终身累计答错次数(含"重复导入触发"的情形,见 5.2) |
| next_review_date | date,可空 | 下次该复盘的日期;`status = mastered` 时为 NULL,表示当前没有排定的复盘日期 |
| last_reviewed_date | date,可空 | 上次复盘日期 |
| created_at / updated_at | timestamp | 常规记录时间戳 |

唯一性约束:`(term, part, scenario_major, scenario_minor, skill)` 组合用于导入查重判断。其中 `term` 的比较方式是:转小写、去掉所有空格、去掉连字符(`-`)和英文撇号(`'`)后再比较,所以 "check-in"、"check in"、"checkin" 会被判定为同一个 term;这个归一化只用于查重比较,不影响数据库里实际存的原文显示。同一个词/短语在不同场景下可能是完全不同的含义(例如 "check" 在金融场景是支票、在办公室场景是核对),所以查重必须把场景也纳入判断,否则会把两个不同含义的知识点错误合并成一条。约束里包含 `skill` 是为未来 Reading 模块预留:`skill` 当前固定为 'listening',现在加不加这个字段效果上没区别,但等以后 Reading 模块真接入、出现 `skill = 'reading'` 的记录时,能避免和听力的同名知识点被误判成同一条。

手动编辑已有记录的 `part`、`scenario_major` 或 `scenario_minor` 时,同样要按这个唯一性组合校验:若改动后会跟另一条已存在的记录(自身除外)完全重复,阻止保存并提示"这个组合已经存在,请检查是否要合并",不允许出现两条完全相同组合的记录。这条唯一性约束只在 `status != 'deleted'` 的记录之间生效(数据库层面用部分唯一索引实现),所以同一个组合可以同时存在一条 `deleted` 的旧记录和一条全新的 `active` 记录,不会冲突。

**mastered 记录被手动编辑时的状态延续**:手动修改 `meaning`/`example`/`notes` 纯粹是更正描述性文字,不代表"又不会了",不影响 `status` 和 `next_review_date`(mastered 记录改完文字依然是 mastered,依然不会出现在复盘队列里)。手动修改 `part`/`scenario_major`/`scenario_minor` 视为调整分类归属,同样不会触发自动复活,但因为这几个字段是唯一键的一部分,改动后需要重新通过上面那条唯一性校验。

## 5. 导入流程

1. 用户每天在电脑上把当天新增的错题笔记(PDF/Word,只含当天新内容,不是累计文档)上传。
2. 后端将文档转为文字,调用 Claude API 解析为结构化记录:term、meaning、example、notes(如有)、part 与 date_added(从文档中的"Part几"标题和"时间:"行继承)。
3. 若某条记录缺 meaning 或 example,由 AI 生成合理的简洁内容补全;notes 字段不做这种补全,留空即可。
4. Claude 同时依据第 12 节附录的场景分类表,给每条记录判断 scenario_major 和 scenario_minor 两级标签;任何一级拿不准就标"未分类"。
5. 解析结果先展示为可编辑确认列表(meaning、example、notes、part、scenario_major、scenario_minor 都可直接修改/删除),用户确认无误后才正式写入数据库。**`term` 例外,确认列表里只展示不可编辑**(2026-06-29 修订)——term 是这条知识点的主体,改 term 等于换了一个完全不同的词,跟"修正这条记录的分类/释义错误"性质不同;真要换词应该删除这一条、自己手动新增,不属于"确认导入时校正 AI 解析错误"这个场景。
6. 写入时按 `(term, part, scenario_major, scenario_minor, skill)` 查重,并结合 `date_added` 判断是误传重复还是真的又错一次,分情况处理(细节见 5.2)。若某一条写入失败(例如需要人工决定保留哪个版本的文字),只影响这一条,其它正常的记录照常写入,不做整批回滚。

### 5.1 为什么改成"每日小份导入"而不是"累计大文档重复导入"

用户原本习惯把笔记写在同一份持续累加的文档里,每隔几天整份重新导入。这样每次导入都要重新处理全部历史内容,AI 解析的 token 消耗会随文档增长线性上升。改为"每天只导出/导入当天新增内容"后,每次导入的处理量只跟当天新增内容成正比,不会随历史积累变慢变贵,且不需要额外的"按内容指纹跳过已处理区块"机制,简化了实现。

### 5.2 重复匹配后的处理:用 date_added 区分"又错了一次"还是"误传同一份笔记"

当导入的某条记录命中已有记录的唯一键 `(term, part, scenario_major, scenario_minor, skill)` 时,系统进一步比较两者的 `date_added` 来判断这到底是什么情况,而不是直接按"文字内容是否一致"或"用户选保留哪个版本"来判断——这两件事(是否真的又错一次 / 文字措辞用哪个版本)是分开的,不互相耦合:

- **date_added 相同**:大概率是同一份笔记被重复上传(比如手误把同一天的文件传了两次),不是真的又出错一次。直接跳过、不写入、不触发任何调度逻辑(`correct_streak`、`wrong_count`、`next_review_date`、`status` 全部不变),确认列表里标注"与现有记录完全相同,已跳过"。
- **date_added 不同**(新导入的日期比已有记录晚):代表用户在真实听力练习中,在不同的一天又把这个知识点搞错了一次。**无条件**触发"答错"逻辑,跟 meaning/example/notes 的文字内容是否也变了完全无关:
  - 若该记录当前是 **active**:`correct_streak` 清零、`wrong_count + 1`、`next_review_date` 设为明天。
  - 若该记录当前是 **mastered**:自动复活——`status` 改回 active、`correct_streak` 清零、`wrong_count + 1`、`next_review_date` 设为明天。
  - 若这种情况下 `meaning`/`example`/`notes` 的文字内容恰好也变了(比如新笔记的措辞跟旧的不一样),额外标出新旧差异,问用户保留哪个版本的文字——但这个选择只决定显示文字用哪个版本,不会反过来影响上面已经判定的答错逻辑。
- **全新组合(不存在任何匹配,或唯一键匹配上的记录是 `deleted` 状态)**:作为全新记录插入,`status = active`、`correct_streak = 0`、`next_review_date = 今天`(当天即可被抽到复盘,满足"当天抽查刚学内容"的需求)。`deleted` 的记录不参与查重匹配——用户当时判定"不需要再复习",但如果真在听力练习里又遇到同一个知识点出错,这是值得重新开始追踪的新信号,不应该被一条已经删除的旧记录挡住。

`date_added` 本身跟其他字段一样,用户在确认列表或之后的编辑界面里都可以随时手动修改去更正笔误;这种手动修改是独立的用户操作,不会触发上面这套自动判断逻辑(那套逻辑只在导入流程内部、写入前自动跑一次)。"之后的编辑界面"具体落地在错题库浏览页(2026-06-29 补充):每条记录旁有"编辑"入口,可修改 meaning/example/notes/part/scenario_major/scenario_minor/date_added(`term` 除外,理由见第 5 节确认列表的同一条规则——term 是主体,改 term 等于换了一个词)。

### 5.3 场景分类的硬校验兜底

AI 是自由文本生成,即使提示词要求"只能从附录列表里选",仍可能输出列表之外的词(例如把"投资"判断成"股票交易"这种列表里没有的细类)。后端在拿到 AI 的分类结果后,统一跟第 12 节附录的白名单做一次比对:

- `scenario_major` 不在 14 个大类之内,或 `scenario_minor` 不在该大类允许的细类列表(含通用兜底"未分类")之内:强制降级为"未分类",并在确认列表里给这一条标出明显提示(例如标黄)"AI 分类未命中,已自动归为未分类,请手动校正"。
- 这样无论 AI 输出什么,都不会出现入库失败,也不会让脏数据(不在白名单内的细类)进入数据库。

### 5.4 文档格式与解析失败处理

- 支持范围:文字版 PDF/Word(可直接提取文字的格式);不支持扫描图片版 PDF/OCR 识别——这次不做,以后如果笔记习惯变成手写扫描件再考虑加。
- 单次上传文件大小设一个合理上限(例如 5MB),日常单日新增笔记的体量远小于这个量级,正常使用不会触发。
- 上传格式不支持时,前端明确提示"不支持此文件格式,请上传文字版 PDF 或 Word"。
- AI 解析调用失败(超时/接口报错)或返回内容无法识别成结构化数据时,前端提示"解析失败,请重试";不会无声失败,也不会保存任何半成品数据。
- 提供独立的"手动添加一条知识点"入口(不依赖文档导入),可随时单独补一条记录,也作为解析持续失败时的退路。这个入口里 `term`、`part` 需要用户手动填;`meaning`/`example`/`scenario_major`/`scenario_minor` 默认留空,旁边提供一个"AI 自动补全"按钮——用户点了才调用 Claude 根据 term(和已填的 part)生成释义/例句并判断场景,不点就完全手动填,不强制依赖 AI。
- **单次文档按"每 Part/时间 段落不超过 20 条"自动分批调用 AI,各批并行请求**(2026-06-28 修订)。最初实现是整篇笔记一次性塞给 AI,实测一天 123 条这种正常量级就会导致单次生成超出模型输出上限,被截断报错(且单纯调大输出上限上限治标不治本——上限越调大、等待时间越长,几分钟级的等待不可接受)。改为按笔记里的编号条目自动切分成多批,每批保留所在的"Part/时间"上下文,各批同时并行调用 AI 再合并结果,避免单次调用规模随文档总量线性增长,与上传体量无关,用户侧的上传/确认流程不变。
  - 切分逻辑按字符位置定位"时间：""Part几""编号条目"这三种标记,不依赖真实换行符——PDF 提取文字时不会保留原始排版的换行(实测真实 PDF 整篇笔记被拉平成一行),按行识别的方案在这种情况下完全失效。日期标记会一直沿用到下一个日期标记出现为止,即使中间的 Part 分组没有重复写"时间："。同时排除条目内容里偶然提到"Part1"这种文字(如"hang 是 Part1 动作动词高频")被误判成新分组标题的情况——真正的分组标题后面一定紧跟编号"1."重新开始,偶然提及的不会。
  - **AI 偶尔不遵守约定的结构化返回格式**(2026-06-28 追加修订,实测真实文档命中率约 3-4/8 批次)。模型在批次内容信息密度较高时(尤其带国际音标标注的条目),偶尔会把 `items` 写成一段"看起来像 JSON 的文字"而不是真正的数组,且这段文字里如果包含笔记原文自带的直角引号(用户习惯用引号强调某个词,如此处不要理解成"文件备份"),还经常忘记转义,导致连"当字符串重新解析一次"这种兜底都会失败。修复分三层:①在提示词里明确要求"严格只用约定字段、不要把 items 包装成字符串";②引入专门处理"AI 生成的 JSON 转义错误"场景的 `jsonrepair` 库做修复,而不是依赖严格的 `JSON.parse`;③单批次修复后仍失败的话自动重试(最多 3 次,有一定随机性,重试有机会成功),但"生成内容超出单批输出上限"这种确定性失败不重试(原样重试只会在同样位置再截断一次)。三层叠加后,用真实文档(2 个日期、5 个 Part 分组、139 条)验证 100% 全部解析成功。

## 6. 复盘流程与交互

1. "今日复盘"页面拉取所有 `next_review_date ≤ 今天` 且 `status = active` 的记录,按优先级排序(`wrong_count` 高、拖欠天数久的排前面),支持按场景(大类/细类)筛选,只复盘某个场景的到期内容,方便针对薄弱场景集中练习。
2. 逐条展示:先只显示 `term` → 用户点击"记得"或"不记得"(揭示答案前的主动回忆判断)→ 系统揭示 `meaning` + `example` + `notes`(如有)→ 用户自行核对,若发现刚才判断错了可以点"撤回"改选另一项 → 确认无误后点击"下一个"。
3. **彻底不需要复习的删除**:卡片在任何阶段(无论还没揭示答案、还是已经揭示答案在核对)都有一个"删除"入口。点击后这条知识点立即从复盘队列消失、跳到下一条,不计入这次的对/错(不影响 `correct_streak`/`wrong_count`),`status` 改为 `deleted`。删除后出现几秒"已删除「xxx」 撤销"提示,在窗口内点撤销会把 `status` 改回 `active`(`next_review_date` 不变);过了这个窗口就是最终结果。`deleted` 是软删除——记录还在数据库里(支持撤销、也会留在第 10 节的 JSON 导出里),只是彻底退出复盘队列和错题库列表,不会再在任何地方被主动展示。
4. **撤回的边界**(指"记得/不记得"的判断,不是上面的删除撤销):只在点击"下一个"之前有效;一旦进入下一条,上一条的结果即为最终结果,不可逆。因为在点击"下一个"之前什么都还没有写入数据库,撤回只是改变前端尚未提交的选择,不涉及任何数据库回滚。
5. 点击"下一个"时才正式落库这次结果(规则见第 7 节)。当前会话内用户可以随时关闭页面,未复盘的到期记录不会丢失,下次打开依然在队列里(只是会因为拖欠更久而排得更靠前)。
6. 队列为空时显示"今天没有需要复盘的内容"。
7. 错题库列表(非复盘模式,纯浏览)支持按 Part、按场景(大类/细类)筛选,同样可以直接删除某条记录(同样是软删除,带撤销提示)。
8. "已掌握"列表可单独查看所有 mastered 记录,并提供手动"移回错题库"操作(重置为 `status = active`、`correct_streak = 0`、`next_review_date = 今天`,立刻进入当天的复盘队列)。由于会清零连续答对次数,操作前需要用户二次确认(2026-06-29 修订);确认后给出"已移回错题库,今天会重新出现在复盘队列"的提示。
   - **跨页面实时刷新已放宽**(2026-06-29 修订)。最初设计是"若操作时『今日复盘』页面已经打开过、队列已经加载在前端,移回操作完成后前端会重新拉取一次队列,不需要用户手动刷新页面才能看到这条记录"——这是针对单页应用里两个页面同时挂载、共享状态的场景。实际是单人使用的独立页面跳转(SPA 路由),每次导航到"今日复盘"本身就会重新拉取队列,不存在"已经打开的旧队列需要被动刷新"的情况;这条要求对当前架构没有实际意义,不需要额外搭一套跨页面的状态同步机制,按"导航到页面即重新拉取"处理即可。

## 7. 间隔复盘算法

基础曲线 `CURVE = [1, 2, 4, 7, 15, 30]`(天),是经典艾宾浩斯记忆曲线的常见取值,一路答对不间断的话累计约 59 天——跟托业备考常见的 2-3 个月(60-90 天)总时间跨度基本匹配。`correct_streak`(连续答对次数,任意一次答错清零)仍然是唯一驱动这套调度的字段,不再单独存"曲线档位":正常情况下(没有被答错打断)它和"走到曲线第几档"是同一个数。

- **答对(最终判定)**:`correct_count += 1`、`correct_streak += 1`,记 `k = correct_streak`。
  - 若 `k <= 6`:`next_review_date = 今天 + CURVE[k-1]` 天(第1次连续答对等1天、第2次2天、第3次4天、第4次7天、第5次15天、第6次30天)。
  - 若 `k >= 7`(即在间隔满 30 天之后又答对了一次):`status = mastered`,移出每日复盘队列,不再设置 next_review_date。要走到这一步,必须完整撑过曲线全部 6 个间隔、连一次都没答错,才会被认定为真正长期记住,不会因为这几天短期记忆好、连对两三次就被提前判定"已掌握"。
- **答错(最终判定)**:`wrong_count += 1`、`correct_streak = 0`,`next_review_date = 今天`(不是明天)——这条记录仍然到期,会留在今天的复盘队列里,而不是消失到明天才再出现。下次答对时按"连续答对第1次"正常处理,重新从"1天后"开始算,整条曲线从头走一遍。

由于答错会清零连续答对数,"常错的知识点"会一直停留在曲线最前端、被高频抽到复盘,无需额外设计加频规则。

**当天必须答对一次才算过关**(2026-06-28 修订,推翻了本节最初的设计):最初的设计是答错直接排到明天,理由是这样"今日复盘"只需拉取 `next_review_date ≤ 今天` 的记录,同一条记录天然不会在同一天内被重复抽到,不需要额外的"每日复盘次数上限"机制,逻辑更简单。但实测下来用户更希望"今天错的,今天就该改正",而不是错一次就拖到明天。改为答错保持 `next_review_date = 今天` 后:
- 后端层面这条记录依然满足"今日复盘"的拉取条件,不需要改查询逻辑。
- 前端(`src/app/review/page.tsx`)在用户选错并点"下一个"提交结果后,把这道题重新塞回当前会话本地队列数组的末尾,这样它会在本次复盘session结束之前再被抽到一次,而不是只在下次重新打开页面时才出现。重新抽到后答对,就正常按上面"连续答对第1次"的规则处理(明天到期),退出当天队列。
- 代价是确实放弃了"同一条记录不会同一天内重复抽到"这条不变量,但只在"刚答错"这一种情况下成立,且是有意为之的行为,不是 bug。

如果实际备考时间不到 2 个月,大部分知识点可能在考试前都没机会真正"毕业",会一直留在每日复盘队列里——这是预期内的行为,宁可多复盘也不提前误判为已掌握。

## 8. 模考成绩记录

独立入口"记录一次模考":用户输入模考日期,必须填写 Part1-4 各自的对题数/总题数,可选填任意数量的"场景(大类+细类):对题数/总题数"。保存后出现在统计页面的"模考历史"列表中,按日期排列,用于发现长期偏弱的 Part 或场景。这套数据与错题库的复盘记录完全独立,互不影响对方的计算逻辑。

校验规则:每个填写的"对题数/总题数"(无论是 Part 还是场景细分)都要求总题数 ≥ 1 且对题数 ≤ 总题数,不允许 0/0 或负数,避免计算正确率时出现除零或运行时错误;不满足时前端直接阻止保存并提示哪一项有问题。

## 9. 统计页面

两个独立区块:

1. **错题库统计**:当前 active 记录数、mastered 记录数、按 Part 汇总的历史正确率、按场景大类汇总的历史正确率(`correct_count / (correct_count + wrong_count)`)。统计范围只包含 `status` 为 active 或 mastered 的记录,`deleted` 的记录不计入任何统计,等同于从这些汇总里完全抹去。数据来源是 `knowledge_points` 表上的聚合字段,不依赖单独的事件日志表。细类层级的数据仍然存在,但本次统计页面只展示大类层级的汇总图表;需要细类明细时可在错题库列表里按细类筛选查看,不在统计页面单独再做一层图表,避免本次范围过度扩大。
2. **模考历史**:按时间列出每次模考记录的 Part/场景正确率,表格形式,本次不做趋势图表。

## 10. 数据导出与备份

在统计页面提供一个"导出全部数据"按钮,点击后把 `knowledge_points`、`mock_exam_results`、`mock_exam_scenario_scores` 三张表的全部数据打包成一个 JSON 文件,由浏览器直接下载到本机,作为额外的手动备份手段。导出范围是数据库里的全部记录,不按 `status` 过滤,`deleted` 的记录也会包含在内,留一份完整存档。

不做自动定时备份、不做云端多版本备份机制——Vercel Postgres(底层是 Neon)本身通常自带一定程度的平台级时间点恢复能力,具体保留时长以实际开通时的版本为准;这个导出按钮只是想要更安心时随手点一下的额外保险,不是依赖它做灾难恢复的主要手段。

## 11. 安全与运行默认值

- 密码门:单一共享密码,存为 Vercel 环境变量,纯文本比较;验证后用 cookie 维持会话,cookie 设 30 天有效期,过期需重新输入密码。
- API Key(Anthropic):存为 Vercel 环境变量,不进入代码仓库或前端。
- 时区:统一按中国时间(UTC+8)计算"今天"以及到期日判断。
- 查重比较时对 `term` 做归一化:转小写、去掉所有空格、去掉连字符和英文撇号后再比较(详见 4.1)。
- 忘记密码:无自助找回流程,需要请求修改 Vercel 环境变量并重新部署。
